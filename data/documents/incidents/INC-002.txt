Executive Summary

On October 8, 2025, a significant infrastructure incident affected the Amazon EKS production environment supporting multiple AetherAI Cloud services. A failure within a worker node group caused workload disruption across the Enterprise RAG Platform, Inference Platform, Evaluation Engine, and internal monitoring services.

Although Kubernetes self-healing mechanisms successfully rescheduled a portion of affected workloads, capacity constraints within the cluster delayed full recovery and resulted in elevated latency, intermittent service degradation, and temporary workload unavailability.

The incident did not result in data loss but exposed weaknesses in node pool capacity planning and automated recovery processes.

Investigation

Initial investigation focused on:

• Kubernetes events
• EC2 instance health
• Auto Scaling Group status
• Resource utilization metrics

Analysis confirmed that multiple nodes within the same node group entered an unhealthy state simultaneously.

Root Cause Analysis

Primary Root Cause

A defective operating system patch introduced during a routine node image update caused kernel-level instability on newly provisioned worker nodes.

The issue triggered:

• Unexpected node restarts
• Kubelet instability
• Container runtime failures
• Network interface disruptions

Affected nodes repeatedly failed health checks and were removed from service.

Contributing Factors

Insufficient Canary Testing

The updated node image was tested in staging but did not fully replicate production workload characteristics.

Node Group Concentration Risk

Several critical workloads were heavily concentrated within a single node group.

Capacity Constraints

Cluster reserve capacity was insufficient to absorb simultaneous node failures without performance degradation.

Delayed Autoscaling Response

Autoscaling policies reacted slower than expected under rapid capacity loss conditions.

Technical Findings

Investigation identified:

• Repeated kernel panic events
• Kubelet restart loops
• Failed container networking initialization
• Elevated pod scheduling failures

Approximately 35 percent of worker node capacity became unavailable during the incident.

Containment Actions

Immediate containment actions included:

1. Suspend deployment of the affected node image.
2. Block additional node provisioning.
3. Redirect workloads to healthy node groups.
4. Increase cluster monitoring frequency.
5. Freeze non-essential production changes.

Containment prevented further propagation of the issue.

Resolution

Recovery activities occurred in four phases.

Phase 1: Image Rollback

Actions:

• Revert node image version
• Disable defective AMI
• Validate cluster stability

Phase 2: Capacity Restoration

Actions:

• Launch healthy replacement nodes
• Expand cluster capacity
• Validate scheduling functionality

Phase 3: Workload Recovery

Actions:

• Reschedule evicted pods
• Restart affected services
• Validate application health

Phase 4: Operational Validation

Actions:

• Verify cluster metrics
• Review service performance
• Confirm workload stability

Recovery validation was completed successfully.

Areas for Improvement

• Cluster reserve capacity was too low.

Long-Term Recommendations

Approved initiatives include:

• Blue-green node pool deployments
• Automated node health validation
• Enhanced workload spreading policies
• Regional failover readiness testing
• Capacity forecasting improvements

Recommendations were assigned to Platform Engineering and Site Reliability Engineering teams.

Summary

The EKS Node Failure incident resulted from a defective operating system image update that introduced kernel instability within production worker nodes. The resulting capacity reduction caused service degradation across multiple AetherAI Cloud platforms. Through rapid containment, image rollback, cluster recovery, and workload redistribution, services were restored without data loss. The incident reinforced the importance of infrastructure validation, capacity planning, workload isolation, and automated recovery controls within Kubernetes-based production environments.
